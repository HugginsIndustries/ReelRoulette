# ReelRoulette Repository Context

This document is the high-level capability and ownership map for contributors and agents.
Keep it concise and current. Do not use it as a milestone changelog.

## Purpose and Architecture Direction

ReelRoulette is a thin-client, API-first system:

- Core/server owns domain logic and authoritative state.
- The WebUI is the only client, an orchestration/render layer over API + SSE.
- Shared contracts (`shared/api/openapi.yaml`) drive the WebUI's requests and the generated types it checks them against.

## Current Implemented Capabilities

- **Server host (`src/core/ReelRoulette.ServerApp`)**
  - Default single-process runtime serving API, SSE, media, WebUI assets, and Operator UI.
  - Control-plane surfaces under `/control/*` for runtime status/settings/pairing/lifecycle/testing/logs.
  - Localhost means a direct connection from the server machine, decided by one check: from loopback, or to the server's own address from that address. A request through a reverse proxy is never localhost, even when the proxy runs on the server machine, and neither is one with no remote address. Forwarded headers are applied only from loopback, one hop, so behind a proxy on the server machine the request takes the client's address, scheme, and host; cookies are `Secure` over the proxy's HTTPS, and `/runtime-config.json` returns its `https://` URLs. Forwarded headers from any other address are ignored and logged once per address.
  - **Allow remote connections** (`bindOnLan`) off refuses every request from another device with 403, directly or through a proxy, on every path; on, the server also listens on the LAN from its next start.
  - API pairing covers `/api` routes only. The WebUI's files, `/runtime-config.json`, and `/operator` load for every caller, and the runtime config includes the pairing token only for a caller that pairing already accepts, so an unpaired device reaches the pairing prompt.
  - Localhost control requests are trusted, testing routes included. Every non-localhost control request needs the control token, through a `POST /control/pair` admin cookie or the token as a bearer header, never a query parameter, and there is no setting that turns this off. The server generates and saves a control token on start when none is set. Changing the token ends every control session and gives a non-localhost caller that changed it a fresh one, and a failed pairing attempt logs a warning with the remote address. A control session also authorizes API requests. On another machine the Operator shows only a control token prompt until a valid token is entered.
  - Operator testing mode supports deterministic fault simulation (version/capability mismatch, API unavailable, media missing, SSE disconnect).
  - mDNS LAN hostname advertisement for WebUI when enabled.
  - `REELROULETTE_DATA_DIR` moves the server's settings, catalog, backups, `last.log`, and thumbnails (`<folder>/thumbnails`) to one folder on every OS; unset, the server uses `ApplicationData/ReelRoulette` and `LocalApplicationData/ReelRoulette/thumbnails`. Server-starting verification scripts and the core test run set it to a temporary folder.
  - `last.log` lines from the server and from `POST /api/logs/client` go through one writer under a process-wide lock, one line per entry. Relayed WebUI lines carry no file paths or file names; the server's own source import and backup lines still show paths.
  - When the server starts stopping, it ends open event streams and cuts media responses still being sent, so stop, restart, and update apply do not wait for connected clients.
  - Host-UI abstraction keeps server runtime tray-agnostic:
    - Uses a cross-platform Avalonia tray host when available (lifecycle/refresh/operator shortcuts). The tray runs until the server shuts it down, always on the tray's UI thread. If the tray ends without that, `last.log` records it and the server keeps running.
    - The tray loads the Fluent theme, since on Windows Avalonia draws the tray menu as its own window. `last.log` records tray icon clicks, each time the Windows tray menu opens (with its size and item count) and closes, failed or rejected tray menu actions, tray UI errors, and Avalonia warnings and errors, each written once per run.
    - Falls back to a deterministic headless host when a tray cannot be created.
  - The server's executable and tray icon is `assets/logo/app.ico`, copied next to the executable.
  - Startup-launch registration is host-managed with immediate toggle support through tray and Operator control settings:
    - Windows: user-scoped `HKCU` registration.
    - Linux: XDG autostart (`*.desktop` under `~/.config/autostart/` or `$XDG_CONFIG_HOME/autostart/`, with `Exec=`/`Path=` derived from the stable app path—**`APPIMAGE`** when running an AppImage, otherwise the process path—and host content root pinned to `AppContext.BaseDirectory` so session autostart finds config and WebUI assets).
  - Packaged server builds self-update via Velopack on an operator-controlled check → download → apply flow: a background loop checks the feed only (stable or dev via `devChannelEnabled` on `/control/settings`) to surface availability; download and apply are separate confirmed operator actions under `/control/update/*` and never run automatically; an immediate check still runs when the dev channel toggle changes.
  - On Linux, when running a Velopack **AppImage** (`APPIMAGE` set), the server reconciles a Freedesktop application menu entry (`reelroulette-server.desktop`) and hicolor icons under the user’s XDG data home on every launch—silent, with no first-run flag; `Exec=` always points at the current AppImage path. The icons are the logo's 256 px PNG and its scalable SVG, and an old 512 px icon left by an earlier install is removed.

- **Domain execution (`src/core/ReelRoulette.Core` + server services)**
  - API-authoritative library operations (import, duplicates, auto-tag, playback stats, refresh pipeline).
  - The server opens a SQLite `library.db` at startup (WAL, synchronous=NORMAL, `user_version` 6). A catalog at an older version from 2 is upgraded in place on open in one transaction, one step per version, and `last.log` records it: version 2 to 3 adds the stored file name sort key and the sort indexes and drops the item tag index that duplicates its primary key and the file name fold index that no query uses, version 3 to 4 adds each item's loudness analysis version, clears every stored peak, and marks every video as scanned under analysis version 1, version 4 to 5 gives each preset an id of its own, kept across renames, and writes each stored preset's `favoritesMode` and `blacklistedMode` in place of the older `favoritesOnly` and `excludeBlacklisted`, so it filters as it did, and version 5 to 6 counts each video whose loudness scan measured digital silence as a video without audio, with no rescan. An upgrade that cannot run leaves the catalog unchanged and is reported like a catalog that cannot be read. A `library.db`, `library.db.previous`, or `library.db.incoming` that a newer version saved, or that cannot be opened or read at the moment, is left unchanged. A database at a schema version before 2, or one whose schema or revision row shows it is not a database or is corrupt, is moved aside to `library.db.refused`. An empty database is created only when there is no `library.db`, no `library.db.refused*` file, and no `library.db.backup.*` file. Otherwise the server runs without a library: `last.log` gets a warning with the reason, `/control/status` and `/api/version` report it in `libraryState` and `libraryMessage`, the Operator page shows it, every `/api` route except version, capabilities, pairing, web runtime, backup and refresh settings, and client log relay answers 503 with it, and neither catalog backups nor refresh run. A healthy database is the live catalog: readers and writers update affected rows. `GET /api/library/catalog-checkpoint` returns a standalone copy of that database. Server catalog backups store the same kind of copy. Backup rotation trims only valid current-version backups, and other files in `backups/` stay. `POST /api/library/query` is the browse path: enabled sources, then filename or relative-path search, then filter, then sort, with `totalCount`, `searchBaselineCount`, and thumbnail layout fields on the returned page, including a `thumbnailVersion` that changes whenever the JPEG is written again. `GET /api/thumbnail/{itemId}` sends an ETag and `Last-Modified`; requested with that version as `v`, it is cacheable as immutable, and otherwise it is `no-cache`. Every sort mode and direction reads its own index, and name order and name tie-breaks use the stored sort key, which orders like OrdinalIgnoreCase but takes its casing from .NET's built-in Unicode table rather than the system's ICU, so the key is the same on every system. Both counts are cached until the next catalog write, so later pages, appends, and reloads of the same query do not count again. A page holds up to 10,000 items, and each request writes one `last.log` line with its elapsed time. A filter's `favoritesMode` and `blacklistedMode` each keep only those items, leave them out, or ignore them, and the older `favoritesOnly` and `excludeBlacklisted` are ignored. Random selection uses that filter, plus the request's video and photo options, reads only each eligible item's id, path, play count, and last played, then reads the picked item by id, and does not keep a full-catalog cache. Smart shuffle's bag holds item ids and starts over when the set of eligible ids or the mode changes. Each pick writes one `last.log` line with the mode, eligible count, and elapsed time. Playing one item reads that item and whether its source is enabled. `POST /api/library/item` reads one item by its catalog id and does not add thumbnail fields. Library stats include the loudness baseline. An empty stored source display name is omitted. Tag-editor model reads, item-tag add and remove, category and tag upsert, rename, and delete, and auto-tag apply update catalog rows. Favorite, blacklist, record-playback, and clear-stats update those rows, finding items by catalog id only, so a full path finds no item; auto-tag apply alone finds its files by full path. A favorite clears blacklist, and a blacklist clears favorite. Clear-stats clears every played row only with `allItems`, and an id list clears only those items; a request with neither, or both, is refused and clears nothing. Library stats are one SQL pass grouped by source id and media type: an item counts toward the source whose id it holds, and is a photo when its media type is photo and a video otherwise. Auto-tag scan and duplicate scan read catalog rows. A full-library auto-tag scan reads every item, and any other scan reads enabled sources. Duplicate groups include only ready fingerprints. Duplicate apply deletes the non-kept files and rows. Source import inserts new files and updates existing paths. The disk walk does not hold the catalog lock. An existing path keeps its id, tags, favorite, blacklist, and playback stats. Files missing on disk stay until refresh. Refresh removes items whose files are gone, except from a disabled source, a source whose folder is missing, or a source whose folder exists but lists no media files while the library holds items from it, such as a mount point whose drive or share isn't mounted: those items stay, and in that last case `last.log` gets a warning naming the folder, and the refresh status lists the source by id with its kept item count in `keptSources`, which each run starts empty. Refresh writes the columns each stage owns as that work finishes. A favorite, tag, blacklist, or playback change that commits during a stage stays. Thumbnail reuse trusts the revision stored on the item, which is that item's fingerprint, size, and write time, and does not walk those source files when that revision still matches. The stage writes that item's revision, width, and height as the item finishes. Browse reads those dimensions from the item row. `hasThumbnail` is still whether that item's JPEG exists. When the thumbnail stage completes, a JPEG whose item is not in the catalog is deleted, and the finished refresh's summary reports that cleanup. Opening the catalog does not delete those files. There is no thumbnail file-count or byte cap. A catalog backup for that refresh is taken after the refresh finishes and still follows the backup gap. A shorter backup gap applies on the next catalog save. Opening the catalog does not read it whole. The source list and source enable and disable read catalog rows, so an imported source is listed and can be toggled without a restart. The tag table is the catalog's tag list. An item can still hold a tag name that is not in that table.
  - `POST /api/play/{itemId}` (persisted library **id** only): returns the same `RandomResponse` shape as random playback, records playback server-side, and emits `playbackRecorded` on SSE; deterministic `404` / `409` / `415` errors with optional `code` on `ErrorResponse`. The play read is that item and its source. Direct play does not block blacklisted items; callers must not double-call `record-playback` for the same start.
  - Presets: each has an id of its own, kept across renames, which `GET /api/presets` returns and the random request's `presetId` names. `POST /api/presets/create`, `POST /api/presets/{presetId}/update`, `POST /api/presets/{presetId}/rename`, `POST /api/presets/reorder`, and `POST /api/presets/{presetId}/delete` write one preset, or the order, and publish `presetCatalogChanged` with the preset's id, or none for a reorder, and the request's `clientId`. A preset holding the default filter, another preset's filter, or another preset's name is refused, and a write the catalog doesn't take answers 500 and gets a `last.log` warning. The WebUI's Filter tab saves each preset it changed through them, one at a time, and every open WebUI reloads its presets on the event.
  - Every event and response that names a library item carries its catalog item id: `RandomResponse.itemId` (its `id` is the full path, which the Stats tab shows), `playbackRecorded.itemId`, `itemTagsChanged.resolvedItemIds`, the record-playback response, auto-tag scan files and apply results, and duplicate-apply failures. `itemStateChanged` also carries `previousIsFavorite` and `previousIsBlacklisted`, and `clientId`, the client whose favorite or blacklist request made the change, which the WebUI sends. Library items carry `durationSeconds` beside the `duration` string. Random picks and library plays (`RandomResponse`) carry the video's `integratedLoudness` and `peakDb` too, null where the loudness scan hasn't measured them, for loudness normalization.
  - Unified refresh pipeline: stage/status projection, a name sort key stage that fills missing keys and recomputes every key after a key version change, thumbnail generation, library **duration** / **loudness** via **ffmpeg**/**ffprobe**, and server-scheduled **auto-refresh**. The loudness scan measures integrated loudness and true peak with `ebur128`, one video at a time, stores no value where it measured none, counts a track it measures as digital silence, at the -70 LUFS floor with no peak, as no audio, the same as a file without an audio track, and records the loudness analysis version, so a video with audio scanned under an older version is scanned again. A scan that fails keeps the stored loudness and peak and records its error, and the next refresh scans that video again. Server shutdown cancels a manual or automatic refresh in progress and does not record that cancellation as a pipeline failure or a completed refresh. Catalog updates that stage has already written stay. A forced duration or loudness rescan stays pending when shutdown cancels that stage. Saving refresh settings schedules the next automatic refresh from the new interval, and clearing a forced rescan keeps the other refresh settings. Clients send refresh **settings** (for example enable/interval) and consume library state via API/SSE only (no authoritative client-side refresh stages or local ffprobe for catalog duration).
  - Replay-aware SSE envelope with reconnect recovery (`Last-Event-ID`, `resyncRequired`, authoritative requery). The WebUI resumes its event stream with the last event ID, and takes the revision of a `resyncRequired` it receives. A stream opened without a last event ID starts with a `streamOpened` event carrying the server's current revision, so a client that receives no other event still resumes from it, including from 0. A last event ID ahead of the server's revision, as after a server restart, gets `resyncRequired`. Duration and loudness refresh progress is published at most every 500 ms, like fingerprint and thumbnail progress, plus each stage's completion.
