# ReelRoulette Repository Context

This document is the high-level capability and ownership map for contributors and agents.
Keep it concise and current. Do not use it as a milestone changelog.

## Purpose and Architecture Direction

ReelRoulette is migrating from a monolithic desktop app to a thin-client, API-first system:

- Core/server owns domain logic and authoritative state.
- Desktop/WebUI are orchestration/render clients over API + SSE.
- Shared contracts (`shared/api/openapi.yaml`) drive cross-client behavior parity.

## Current Implemented Capabilities

- **Server host (`src/core/ReelRoulette.ServerApp`)**
  - Default single-process runtime serving API, SSE, media, WebUI assets, and Operator UI.
  - Control-plane surfaces under `/control/*` for runtime status/settings/pairing/lifecycle/testing/logs.
  - Localhost means a direct connection from the server machine, decided by one check: from loopback, or to the server's own address from that address. A request through a reverse proxy is never localhost, even when the proxy runs on the server machine, and neither is one with no remote address. Forwarded headers are applied only from loopback, one hop, so behind a proxy on the server machine the request takes the client's address, scheme, and host; cookies are `Secure` over the proxy's HTTPS, and `/runtime-config.json` returns its `https://` URLs. Forwarded headers from any other address are ignored and logged once per address.
  - **Allow remote connections** (`bindOnLan`) off refuses every request from another device with 403, directly or through a proxy, on every path; on, the server also listens on the LAN from its next start.
  - API pairing covers `/api` routes only. The WebUI's files, `/runtime-config.json`, and `/operator` load for every caller, and the runtime config includes the pairing token only for a caller that pairing already accepts, so an unpaired device reaches the pairing prompt.
  - Localhost control requests are trusted, testing routes included. Every non-localhost control request needs the control token, through a `POST /control/pair` admin cookie or the token as a bearer header, never a query parameter, and there is no setting that turns this off. The server generates and saves a control token on start when none is set. Changing the token ends every control session and gives a non-localhost caller that changed it a fresh one, and a failed pairing attempt logs a warning with the remote address. A control session also authorizes API requests. On another machine the Operator shows only a control token prompt until a valid token is entered.
  - Operator testing mode supports deterministic fault simulation (version/capability mismatch, API unavailable, media missing, SSE disconnect).
  - mDNS LAN hostname advertisement for WebUI when enabled.
  - `REELROULETTE_DATA_DIR` moves the server's settings, catalog, backups, `last.log`, and thumbnails (`<folder>/thumbnails`) to one folder on every OS; unset, the server uses `ApplicationData/ReelRoulette` and `LocalApplicationData/ReelRoulette/thumbnails`. Server-starting verification scripts and the core test run set it to a temporary folder.
  - `last.log` lines from the server and from `POST /api/logs/client` go through one writer under a process-wide lock, one line per entry. Relayed desktop and WebUI lines carry no file paths or file names; the server's own source import and backup lines still show paths.
  - When the server starts stopping, it ends open event streams and cuts media responses still being sent, so stop, restart, and update apply do not wait for connected clients.
  - Host-UI abstraction keeps server runtime tray-agnostic:
    - Uses a cross-platform Avalonia tray host when available (lifecycle/refresh/operator shortcuts). The tray runs until the server shuts it down, always on the tray's UI thread. If the tray ends without that, `last.log` records it and the server keeps running.
    - The tray loads the Fluent theme, since on Windows Avalonia draws the tray menu as its own window. `last.log` records tray icon clicks, each time the Windows tray menu opens (with its size and item count) and closes, failed or rejected tray menu actions, tray UI errors, and Avalonia warnings and errors, each written once per run.
    - Falls back to a deterministic headless host when a tray cannot be created.
  - The server's executable and tray icon is `assets/logo/app.ico`, copied next to the executable. The desktop client keeps its old `assets/HI.ico`, `HI-256.png`, and `HI-512.png` until it is removed.
  - Startup-launch registration is host-managed with immediate toggle support through tray and Operator control settings:
    - Windows: user-scoped `HKCU` registration.
    - Linux: XDG autostart (`*.desktop` under `~/.config/autostart/` or `$XDG_CONFIG_HOME/autostart/`, with `Exec=`/`Path=` derived from the stable app path—**`APPIMAGE`** when running an AppImage, otherwise the process path—and host content root pinned to `AppContext.BaseDirectory` so session autostart finds config and WebUI assets).
  - Packaged server builds self-update via Velopack on an operator-controlled check → download → apply flow: a background loop checks the feed only (stable or dev via `devChannelEnabled` on `/control/settings`) to surface availability; download and apply are separate confirmed operator actions under `/control/update/*` and never run automatically; an immediate check still runs when the dev channel toggle changes.
  - On Linux, when running a Velopack **AppImage** (`APPIMAGE` set), the server reconciles a Freedesktop application menu entry (`reelroulette-server.desktop`) and hicolor icons under the user’s XDG data home on every launch—silent, with no first-run flag; `Exec=` always points at the current AppImage path. The icons are the logo's 256 px PNG and its scalable SVG, and an old 512 px icon left by an earlier install is removed.
  - The desktop client self-updates via Velopack with the same manual check → download → apply flow in Settings: stable or dev channel via `DevChannelEnabled` in `desktop-settings.json`, background check-only polling, and no restart without explicit Apply confirmation.

- **Domain execution (`src/core/ReelRoulette.Core` + server services)**
  - API-authoritative library operations (import, duplicates, auto-tag, playback stats, refresh pipeline).
  - The server opens a SQLite `library.db` at startup (WAL, synchronous=NORMAL, `user_version` 4). A catalog at an older version from 2 is upgraded in place on open in one transaction, one step per version, and `last.log` records it: version 2 to 3 adds the stored file name sort key and the sort indexes and drops the item tag index that duplicates its primary key and the file name fold index that no query uses, and version 3 to 4 adds each item's loudness analysis version, clears every stored peak, and marks every video as scanned under analysis version 1. An upgrade that cannot run leaves the catalog unchanged and is reported like a catalog that cannot be read. A `library.db`, `library.db.previous`, or `library.db.incoming` that a newer version saved, or that cannot be opened or read at the moment, is left unchanged. A database at a schema version before 2, or one whose schema or revision row shows it is not a database or is corrupt, is moved aside to `library.db.refused`. An empty database is created only when there is no `library.db`, no `library.db.refused*` file, and no `library.db.backup.*` file. Otherwise the server runs without a library: `last.log` gets a warning with the reason, `/control/status` and `/api/version` report it in `libraryState` and `libraryMessage`, the Operator page shows it, every `/api` route except version, capabilities, pairing, web runtime, backup and refresh settings, and client log relay answers 503 with it, and neither catalog backups nor refresh run. A healthy database is the live catalog: readers and writers update affected rows. `GET /api/library/catalog-checkpoint` returns a standalone copy of that database. Server catalog backups store the same kind of copy. Backup rotation trims only valid current-version backups, and other files in `backups/` stay. `POST /api/library/query` is the browse path: enabled sources, then filename or relative-path search, then filter, then sort, with `totalCount`, `searchBaselineCount`, and thumbnail layout fields on the returned page, including a `thumbnailVersion` that changes whenever the JPEG is written again. `GET /api/thumbnail/{itemId}` sends an ETag and `Last-Modified`; requested with that version as `v`, it is cacheable as immutable, and otherwise it is `no-cache`. Every sort mode and direction reads its own index, and name order and name tie-breaks use the stored sort key, which orders like OrdinalIgnoreCase but takes its casing from .NET's built-in Unicode table rather than the system's ICU, so the key is the same on every system. Both counts are cached until the next catalog write, so later pages, appends, and reloads of the same query do not count again. A page holds up to 10,000 items, and each request writes one `last.log` line with its elapsed time. A filter's `favoritesMode` and `blacklistedMode` each keep only those items, leave them out, or ignore them, and a filter with only the older `favoritesOnly` and `excludeBlacklisted` filters as before. Random selection uses that filter, plus the request's video and photo options, reads only each eligible item's id, path, play count, and last played, then reads the picked item by id, and does not keep a full-catalog cache. Smart shuffle's bag holds item ids and starts over when the set of eligible ids or the mode changes. Each pick writes one `last.log` line with the mode, eligible count, and elapsed time. Playing one item reads that item and whether its source is enabled. `POST /api/library/item` reads one item by id or full path and does not add thumbnail fields. Library stats include the loudness baseline. Desktop connect and resync use library stats, sources, and the tag catalog, and read one item for now-playing when that file is not already loaded. An empty stored source display name is omitted. Tag-editor model reads, item-tag add and remove, category and tag upsert, rename, and delete, and auto-tag apply update catalog rows. Favorite, blacklist, record-playback, and clear-stats update those rows. A favorite clears blacklist, and a blacklist clears favorite. Clear-stats with no path list clears every played row. A path list clears only those items. Library stats are one SQL pass grouped by source id and media type: an item counts toward the source whose id it holds, and is a photo when its media type is photo and a video otherwise. An item-state read returns only the requested paths, and an empty path list returns no items. Auto-tag scan and duplicate scan read catalog rows. A full-library auto-tag scan reads every item, a scan with no path list reads enabled sources, and an explicit list matches those full paths. Duplicate groups include only ready fingerprints. Duplicate apply deletes the non-kept files and rows. Source import inserts new files and updates existing paths. The disk walk does not hold the catalog lock. An existing path keeps its id, tags, favorite, blacklist, and playback stats. Files missing on disk stay until refresh. Refresh removes items whose files are gone, except from a disabled source, a source whose folder is missing, or a source whose folder exists but lists no media files while the library holds items from it, such as a mount point whose drive or share isn't mounted: those items stay, and in that last case `last.log` gets a warning naming the folder, and the refresh status lists the source by id with its kept item count in `keptSources`, which each run starts empty. Refresh writes the columns each stage owns as that work finishes. A favorite, tag, blacklist, or playback change that commits during a stage stays. Thumbnail reuse trusts the revision stored on the item, which is that item's fingerprint, size, and write time, and does not walk those source files when that revision still matches. The stage writes that item's revision, width, and height as the item finishes. Browse reads those dimensions from the item row. `hasThumbnail` is still whether that item's JPEG exists. When the thumbnail stage completes, a JPEG whose item is not in the catalog is deleted, and the finished refresh's summary reports that cleanup. Opening the catalog does not delete those files. There is no thumbnail file-count or byte cap. A catalog backup for that refresh is taken after the refresh finishes and still follows the backup gap. A shorter backup gap applies on the next catalog save. Opening the catalog does not read it whole. The source list and source enable and disable read catalog rows, so an imported source is listed and can be toggled without a restart. The tag table is the catalog's tag list. An item can still hold a tag name that is not in that table.
  - `POST /api/play/{itemId}` (persisted library **id** only): returns the same `RandomResponse` shape as random playback, records playback server-side, and emits `playbackRecorded` on SSE; deterministic `404` / `409` / `415` errors with optional `code` on `ErrorResponse`. The play read is that item and its source. Direct play does not block blacklisted items; callers must not double-call `record-playback` for the same start.
  - Every event and response that names a library item carries its catalog item id beside the path fields the desktop reads: `RandomResponse.itemId` (its `id` stays the full path), `playbackRecorded.itemId` with `path` always the catalog's full path, `itemTagsChanged.resolvedItemIds` beside `itemIds` (which can hold full paths), the record-playback response, auto-tag scan files and apply results, and duplicate-apply failures. `itemStateChanged` also carries `previousIsFavorite` and `previousIsBlacklisted`, and `clientId`, the client whose favorite or blacklist request made the change, which the WebUI sends and the desktop doesn't. Library items carry `durationSeconds` beside the `duration` string.
  - Unified refresh pipeline: stage/status projection, a name sort key stage that fills missing keys and recomputes every key after a key version change, thumbnail generation, library **duration** / **loudness** via **ffmpeg**/**ffprobe**, and server-scheduled **auto-refresh**. The loudness scan measures integrated loudness and true peak with `ebur128`, one video at a time, stores no value where it measured none, such as a silent track's peak, and records the loudness analysis version, so a video with audio scanned under an older version is scanned again. A scan that fails keeps the stored loudness and peak and records its error, and the next refresh scans that video again. Server shutdown cancels a manual or automatic refresh in progress and does not record that cancellation as a pipeline failure or a completed refresh. Catalog updates that stage has already written stay. A forced duration or loudness rescan stays pending when shutdown cancels that stage. Saving refresh settings schedules the next automatic refresh from the new interval, and clearing a forced rescan keeps the other refresh settings. Clients send refresh **settings** (for example enable/interval) and consume library state via API/SSE only (no authoritative client-side refresh stages or local ffprobe for catalog duration).
  - Replay-aware SSE envelope with reconnect recovery (`Last-Event-ID`, `resyncRequired`, authoritative requery). Both clients resume their event stream with the last event ID, and take the revision of a `resyncRequired` they receive. A stream opened without a last event ID starts with a `streamOpened` event carrying the server's current revision, so a client that receives no other event still resumes from it, including from 0. A last event ID ahead of the server's revision, as after a server restart, gets `resyncRequired`. Duration and loudness refresh progress is published at most every 500 ms, like fingerprint and thumbnail progress, plus each stage's completion.

- **Desktop client (`src/clients/desktop/ReelRoulette.DesktopApp/`)**
  - Thin-client for migrated flows: API command/query + SSE projection (no dual-writer core-state mutation). Shows library projection from the server (including durations) and syncs refresh-related **settings** to the core; **LibVLC**-backed local playback via `LibVLCSharp.Avalonia` `VideoView` / `MediaPlayer` (`--intf dummy`, re-attach when the native host is ready under Avalonia 12) and `NativeBinaryHelper` / bundled `runtimes/.../native/libvlc` on Windows when present.
  - Local-first playback with deterministic API fallback (`ForceApiPlayback` option). Photo or video for the playing item comes from the server's media type; the desktop keeps no extension list.
  - Saved preset durations are read as the server reads them: a number is seconds. Library sort direction labels match the WebUI's, locked by `shared/fixtures/sort-direction-labels.json`.
  - Library panel is grid-only: an infinite-scrolling justified thumbnail grid with sort (name, last played, play count, duration, **date added**), search, filtering, multi-select, and bulk context-menu actions. Browse uses `POST /api/library/query` for the active filter, search, and sort, and appends further results as the user scrolls. The filtered count is the server `totalCount`. Grid activation requests playback through `POST /api/play/{itemId}` (persisted item **id**); LibVLC renders locally from the returned `RandomResponse` without a duplicate client `record-playback` for the same start.
  - Library panel grid uses API-only thumbnail rendering: layout aspect inputs from the list-query page (`hasThumbnail`, `thumbnailWidth`, `thumbnailHeight`); visible tile JPEGs from `GET /api/thumbnail/{itemId}`; justified-row layout via shared `ReelRoulette.Core.Library.LibraryGridLayout` (no local `thumbnails/` reads for grid display). A page applies thumbnail fields and reflows when an aspect changes, including on the unchanged tiles after an inserted or removed id. Resizing the panel reflows the loaded rows after any in-flight grid update and keeps the viewport tile.
  - Favorite, blacklist, playback, and tag updates patch the loaded tiles when they cannot change which files are shown or their order, and reload that window without jumping to the first page when they can. An interrupted grid update does not shrink the window the next reload requests. Holding the scrollbar during that update does not request further pages, and a filter, sort, or reload deferred by that hold is not appended onto the old tiles. A favorite, blacklist, playback, or tag update while a browse query is open, including a further page that has not been applied yet, reads that query again, including before the first page arrives, so the older page cannot replace the update. A tag event that names an item in neither the loaded tiles nor the current file reloads that window when a tag filter is active, after the rest of the event is applied. The grid takes those updates whether the library panel is shown or hidden.
  - A filter or preset change starts over whether the library panel is shown or hidden. The library preset list shows a saved preset or **None** when the filter matches, and a starred row first (`YouTube*` or `None*`) while it does not. Choosing the starred row leaves the filter in place. Choosing **None** restores the default filter and stays on **None** until that filter changes, even when a saved preset has the same filter. Choosing None in the filter dialog leaves the working filter in place and stays on a saved preset when that filter still equals it. The filter dialog heading is `Preset:` plus that same label. Desktop and WebUI compare the loaded presets in memory the same way: Favorites and Blacklisted compare by resolved mode, so a preset with only the older fields matches the same filter written with the modes, tags compare as case-insensitive sets, source inclusion as a set, and per-category match modes in any category order. Desktop remembers that base, and an explicit **None**, across restart. Preset-list sync does not reload the grid. A library preset pick, **None** included, saves no presets, and the filter dialog's Apply saves the preset list only when it changed.
  - The filter dialog's Favorites and Blacklisted are each a checkbox with an only-or-excluded dropdown, usable while the checkbox is on, and the dialog won't apply or save Favorites only with Blacklisted only. The filter summary names Favorites only, Favorites excluded, and Blacklisted only.
  - Source sync reloads the grid only when an enabled flag changes. A source enable or disable, and auto-tag apply, refresh the loaded window and keep the scroll position. Now-playing favorite, blacklist, tags, playback stats, duration, and loudness read the loaded tile when that file is on screen. A file that is not on screen is read again on play, refresh, resync, and when the runtime connects. A failed read leaves that copy in place unless the server says the file is gone. A favorite, playback, or tag update for the file being read stays, and an update for another file does not drop that read. The current-file section updates when playback of that file starts, and its last-played line is the time before this play, or Never on a first play. A playback event for a file that is not playing yet does not replace it. A playback, favorite, or tag change for the current file does that read when the file is not loaded. A playback for any other missing file still refreshes global play totals. A tag event applies the rest of its items before that read. Connect and resync wait on library stats, sources, and the tag catalog. Header video and photo counts come from those stats. Stats refreshes after events and actions are coalesced: a short wait gathers a burst, one request is in flight at a time, and requests during it get one more. Filter source names come from the sources API, in that API's display-name order. Tag and category lists come from the tag catalog. Volume normalization in auto mode uses the baseline from the last stats response. Scoped auto-tag scan sends `scanFullLibrary: false` and no path list.
  - Library panel grid supports multi-select (click, Ctrl+click, Shift+click), double-click/Enter to play, right-click bulk context menu (favorites, blacklist, tags, clear stats), and selection count display. **Remove from Library** in that menu, and **Rename** and **Remove** in Manage Sources, are hidden until the server has routes for them.
  - Server version/capability compatibility gating with reconnect/resync guidance.
  - On Linux, when running a Velopack **AppImage** (`APPIMAGE` set), the desktop client reconciles `reelroulette-desktop.desktop` and menu icons under the user’s XDG data home on every launch (same silent reconcile semantics as the server).
  - API-backed source import, duplicate scan/apply, auto-tag scan/apply, and playback-stats clear.
  - Duplicate review dialog renders per-item thumbnail previews via server thumbnail endpoint paths for faster keep/delete validation.
  - Duplicate review dialog supports per-group handling selection with a persisted default behavior (`Keep All` or `Select Best`) from desktop settings.
  - `Library → Export Library…` asks for a destination, then saves a server checkpoint as `library.db`. `Import Library…` requires the server-stopped acknowledgment, then replaces that database and can remap source folders. Import replaces presets and thumbnail revision and dimensions with the imported catalog. Settings and backups stay where they are. JPEG files stay in the local thumbnail directory until the next thumbnail stage completes, which generates thumbnails for the imported catalog and removes JPEG files that are not in it. Import upgrades an export at an older schema version, from 2, as it imports it, and refuses to replace a catalog that a newer version saved and leaves it in place. If import fails before the new database is in place, the previous catalog is put back, and a folder that had no catalog is left without one. A cleanup failure after that leaves the imported catalog in place. The overwrite confirmation names the catalog. An existing `library.db` with sources or items asks for it, and so does one that cannot be opened.
  - Duplicate review comparison metadata now includes per-item tag counts and enriched keep-selection labels (filename + plays/tags/favorite/blacklisted) for faster keep decisions.
  - The tag editor closes on save. The current file, now-playing tag line, and loaded tiles show the new tags immediately. The request runs in the background. A failure puts that save's unconfirmed tags back, leaves tags an event already confirmed, and shows an error when anything was restored. A rename or delete updates the applied filter and cached presets before a tag-filter reload. When a file had that tag, the other client renames or deletes it in its applied filter and saved presets before it reloads, then updates the files that had it; a rename or delete of a tag no file has reaches the other client only as `tagCatalogChanged`, without the old name, so it keeps the old name in its applied filter. Auto Tag apply does the same and still reloads the loaded window once when the save lands. Tag editor and filter `Tags` tab share theme-compatible category/chip surfaces in light/dark mode while preserving filter control behavior boundaries.

- **WebUI client (`src/clients/web/ReelRoulette.WebUI`)**
  - Runtime-config bootstrap, direct API/SSE integration, and compatibility/capability checks of `/api/version` at startup, each time the event stream opens, or fails while the server doesn't ask for pairing, and every 3 seconds while the stream is open and the last check didn't reach the server, one at a time, each given up after 10 seconds. Presets, the library, and a panel remembered open load when a check first finds the server compatible with a library, and not again while later checks find it still so. A check answered with 401 counts as not ready, so once the device pairs, the presets load again, the Library tab loads when it has no page, and a Filter or Tags tab that shows loads again.
  - The page is a Preact root with `@preact/signals` shared state. The header (logo, pairing prompt, now playing), the player and its controls (with fullscreen, swipe and tap gestures, and the empty state), the side panel with its Library, Filter, Tags, Stats, and Settings tabs (the library, the filter, the tag editor, the stats, and the settings), Auto Tag, the in-app dialogs, the popups and the list behind the player's bell, and the server connection are components and typed modules. A screen that fails to render stops showing, relays `ui-error screen=<name> error=<type>` to `last.log`, and leaves the others working. A startup error shows its message as text.
  - Session-aware identity propagation (`clientId`/`sessionId`) through API + SSE paths.
  - Core playback/control/tag workflows aligned with server-authoritative behavior.
  - One random pick at a time: a press while one is waiting sends nothing, and a pick the server does not answer within 10 seconds is cancelled, shows "No response from the server. Try again." in the in-app notice, and relays a `playback=random-pick-timeout` line to `last.log`.
  - Player indicator: one lasting state at a time shows at the player's top center at every width, the first active one in this precedence order, so it never alternates: Reconnecting… (`sync`, spinning) while the last version check didn't reach the server, or the event stream has failed and isn't open again, though not before the first check answers, nor while the last check found no library, nor while the server asks for pairing, since the server then refuses the stream; Server not compatible (`sync_problem`, an orange warning) while the server fails the compatibility check; Running without a library (`warning`, orange) while the last check reported a library state other than ready; Loading… (`progress_activity`, spinning) once a random pick, a library play, or a media load has waited half a second, counted once from the first wait until every wait ends, so a quick load shows nothing; and a running refresh, "Library refresh: {stage} ({percent}%)", with the stage's label ("Starting", "Refreshing sources", "Sorting names", "Fingerprinting files", "Scanning durations", "Scanning loudness", "Generating thumbnails"), shown only while the player's controls show, and cleared when a refresh status isn't running and on `resyncRequired`. Reconnecting… ends once the stream is open and a check reaches the server, and Running without a library once a check reports the library ready. Nothing shows while the server asks for pairing. A media load's wait ends on its `playing`, load, or error, a rejected `play()`, or a pause by the user or Auto-Pause, never by a timeout, and buffering partway through a video doesn't count. It stays clear of the corner buttons on both sides and ends a long state in an ellipsis; on a player narrower than 600 px, which the page measures and marks with `is-narrow` on the player column, it sits below them. It is a polite live region that stays in the page, with its icon and a refresh's percentage hidden from screen readers. Each state relays its text to `last.log` once when it starts showing, and a refresh once per stage. None of these states pops up; the list behind the bell shows each active one under Now.
  - A running refresh shows on the player's indicator, and how it ended pops up: "Library refresh finished" with its consolidated summary as the second line, one segment per stage separated by " · ", with the same stage parsing as the desktop client (including Fingerprint segment), or "Library refresh failed" with the server's error as the second line, a warning; `last.log` gets the summary but not the error, which can name a file or folder. A run that ends without finishing or failing, such as one cancelled at shutdown, relays "Core refresh idle." and shows nothing. The theme is the Settings tab's Theme: System, the default, follows `prefers-color-scheme` as it changes, and Dark or Light holds whatever the system says, as `theme-dark` or `theme-light` on the root element, which the stylesheet reads. The `theme-color` meta and `apple-mobile-web-app-status-bar-style` follow the theme in use: `#1a1a1a` and `black-translucent` in the dark theme, `#eceff4` and `default`, for dark status bar text, in the light. An inline script in `index.html`'s head applies the theme kept on this device while the page loads, before it paints and before an installed iOS app reads its status bar style, and the build output check fails unless the built page keeps that script.

Popups sit beside the player at the position the popup settings say, bottom center by default, 12 px up, rising above the player's controls while those show unless the overlay panel covers the player, and on a phone on its side, outside pseudo-fullscreen, clear of the home indicator too; at a top position they start 64 px down, below the indicator on a player narrower than 600 px.
