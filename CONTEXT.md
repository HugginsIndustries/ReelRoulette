# ReelRoulette Repository Context

This document is the high-level capability and ownership map for contributors and agents.
Keep it concise and current. Do not use it as a milestone changelog.

## Purpose and Architecture Direction

ReelRoulette is a thin-client, API-first system:

- Core/server owns domain logic and authoritative state.
- The WebUI is the only client, an orchestration/render layer over API + SSE.
- Shared contracts (`shared/api/openapi.yaml`) drive the WebUI's requests and the generated types it checks them against.

## Current Implemented Capabilities

- **Server host (`src/core/ReelRoulette.ServerApp`)**
  - Default single-process runtime serving API, SSE, media, WebUI assets, and Operator UI.
  - Control-plane surfaces under `/control/*` for runtime status/settings/pairing/lifecycle/testing/logs.
  - Localhost means a direct connection from the server machine, decided by one check: from loopback, or to the server's own address from that address. A request through a reverse proxy is never localhost, even when the proxy runs on the server machine, and neither is one with no remote address. Forwarded headers are applied only from loopback, one hop, so behind a proxy on the server machine the request takes the client's address, scheme, and host; cookies are `Secure` over the proxy's HTTPS, and `/runtime-config.json` returns its `https://` URLs. Forwarded headers from any other address are ignored and logged once per address.
  - **Allow remote connections** (`bindOnLan`) off refuses every request from another device with 403, directly or through a proxy, on every path; on, the server also listens on the LAN from its next start.
  - `POST /api/show-in-file-manager/{itemId}` opens the server machine's file manager with the item's file selected, for a localhost caller only: Explorer with `/select,"<path>"` on Windows, and on Linux the `org.freedesktop.FileManager1` `ShowItems` D-Bus call over a session bus connection of its own, falling back to `xdg-open` on the file's folder when that call fails or there is no session bus, none through a shell. Any other caller gets 403, a server without a desktop, on Linux one with neither `DISPLAY` nor `WAYLAND_DISPLAY` set, 409, and an unknown id or a file that isn't on disk 404. `/api/version` and `/api/capabilities` list `api.showInFileManager` only for a caller it would accept. Each request writes one `last.log` line with the item id and the outcome, without the path.
  - API pairing covers `/api` routes only. The WebUI's files, `/runtime-config.json`, and `/operator` load for every caller, and the runtime config includes the pairing token only for a caller that pairing already accepts, so an unpaired device reaches the pairing prompt.
  - Localhost control requests are trusted, testing routes included. Every non-localhost control request needs the control token, through a `POST /control/pair` admin cookie or the token as a bearer header, never a query parameter, and there is no setting that turns this off. The server generates and saves a control token on start when none is set. Changing the token ends every control session and gives a non-localhost caller that changed it a fresh one, and a failed pairing attempt logs a warning with the remote address. A control session also authorizes API requests. A wrong control token is refused with "The control token is wrong." `GET /control/access` answers 204 to a caller the control check accepts and the control gate's 401 otherwise, so a client learns whether an admin action needs the control token. On another machine the Operator shows only a control token prompt until a valid token is entered.
  - Operator testing mode supports deterministic fault simulation (version/capability mismatch, API unavailable, media missing, SSE disconnect).
  - mDNS LAN hostname advertisement for WebUI when enabled.
  - `REELROULETTE_DATA_DIR` moves the server's settings, catalog, backups, `last.log`, and thumbnails (`<folder>/thumbnails`) to one folder on every OS; unset, the server uses `ApplicationData/ReelRoulette` and `LocalApplicationData/ReelRoulette/thumbnails`. Server-starting verification scripts and the core test run set it to a temporary folder.
  - `last.log` lines from the server and from `POST /api/logs/client` go through one writer under a process-wide lock, one line per entry. Relayed WebUI lines carry no file paths or file names; the server's own source import and backup lines still show paths.
  - When the server starts stopping, it ends open event streams and cuts media responses still being sent, so stop, restart, and update apply do not wait for connected clients.
  - Host-UI abstraction keeps server runtime tray-agnostic:
    - Uses a cross-platform Avalonia tray host when available (lifecycle/refresh/operator shortcuts). The tray runs until the server shuts it down, always on the tray's UI thread. If the tray ends without that, `last.log` records it and the server keeps running.
    - The tray loads the Fluent theme, since on Windows Avalonia draws the tray menu as its own window. `last.log` records tray icon clicks, each time the Windows tray menu opens (with its size and item count) and closes, failed or rejected tray menu actions, tray UI errors, and Avalonia warnings and errors, each written once per run.
    - Falls back to a deterministic headless host when a tray cannot be created.
  - The server's executable and tray icon is `assets/logo/app.ico`, copied next to the executable.
  - Startup-launch registration is host-managed with immediate toggle support through tray and Operator control settings:
    - Windows: user-scoped `HKCU` registration.
    - Linux: XDG autostart (`*.desktop` under `~/.config/autostart/` or `$XDG_CONFIG_HOME/autostart/`, with `Exec=`/`Path=` derived from the stable app path—**`APPIMAGE`** when running an AppImage, otherwise the process path—and host content root pinned to `AppContext.BaseDirectory` so session autostart finds config and WebUI assets).
  - Packaged server builds self-update via Velopack on an operator-controlled check → download → apply flow: a background loop checks the feed only (stable or dev via `devChannelEnabled` on `/control/settings`) to surface availability; download and apply are separate confirmed operator actions under `/control/update/*` and never run automatically; an immediate check still runs when the dev channel toggle changes.
  - On Linux, when running a Velopack **AppImage** (`APPIMAGE` set), the server reconciles a Freedesktop application menu entry (`reelroulette-server.desktop`) and hicolor icons under the user’s XDG data home on every launch—silent, with no first-run flag; `Exec=` always points at the current AppImage path. The icons are the logo's 256 px PNG and its scalable SVG, and an old 512 px icon left by an earlier install is removed.

- **Domain execution (`src/core/ReelRoulette.Core` + server services)**
  - API-authoritative library operations (import, duplicates, auto-tag, playback stats, refresh pipeline).
  - The server opens a SQLite `library.db` at startup (WAL, synchronous=NORMAL, `user_version` 9). A catalog at an older version from 2 is upgraded in place on open in one transaction, one step per version, and `last.log` records it: version 2 to 3 adds the stored file name sort key and the sort indexes and drops the item tag index that duplicates its primary key and the file name fold index that no query uses, version 3 to 4 adds each item's loudness analysis version, clears every stored peak, and marks every video as scanned under analysis version 1, version 4 to 5 gives each preset an id of its own, kept across renames, and writes each stored preset's `favoritesMode` and `blacklistedMode` in place of the older `favoritesOnly` and `excludeBlacklisted`, so it filters as it did, version 5 to 6 counts each video whose loudness scan measured digital silence as a video without audio, with no rescan, version 6 to 7 adds each item's rating, which the catalog stores as a whole number of half stars from 1 to 10, with no value for none, version 7 to 8 adds the rating sort's indexes, and version 8 to 9 adds each item's date added, set to its modified time, with the date added sort's indexes, and renames the modified time's sort indexes for the date created. The `DateAdded` sort orders by the date added and `DateCreated` by the modified time, each through its own indexes. An upgrade that cannot run leaves the catalog unchanged and is reported like a catalog that cannot be read. A `library.db`, `library.db.previous`, or `library.db.incoming` that a newer version saved, or that cannot be opened or read at the moment, is left unchanged. A database at a schema version before 2, or one whose schema or revision row shows it is not a database or is corrupt, is moved aside to `library.db.refused`. An empty database is created only when there is no `library.db`, no `library.db.refused*` file, and no `library.db.backup.*` file. Otherwise the server runs without a library: `last.log` gets a warning with the reason, `/control/status` and `/api/version` report it in `libraryState` and `libraryMessage`, the Operator page shows it, every `/api` route except version, capabilities, pairing, web runtime, backup and refresh settings, and client log relay answers 503 with it, and neither catalog backups nor refresh run. A healthy database is the live catalog: readers and writers update affected rows. `GET /api/library/catalog-checkpoint` returns a standalone copy of that database. Server catalog backups store the same kind of copy. Backup rotation trims only valid current-version backups, and other files in `backups/` stay. `POST /api/library/query` is the browse path: enabled sources, then filename or relative-path search, then filter, then sort, with `totalCount`, `searchBaselineCount`, and thumbnail layout fields on the returned page, including a `thumbnailVersion` that changes whenever the JPEG is written again. `GET /api/thumbnail/{itemId}` sends an ETag and `Last-Modified`; requested with that version as `v`, it is cacheable as immutable, and otherwise it is `no-cache`. Every sort mode and direction reads its own index, and name order and name tie-breaks use the stored sort key, which orders like OrdinalIgnoreCase but takes its casing from .NET's built-in Unicode table rather than the system's ICU, so the key is the same on every system. Both counts are cached until the next catalog write, so later pages, appends, and reloads of the same query do not count again. A page holds up to 10,000 items, and each request writes one `last.log` line with its elapsed time. A filter's `favoritesMode` and `blacklistedMode` each keep only those items, leave them out, or ignore them, and the older `favoritesOnly` and `excludeBlacklisted` are ignored. Random selection uses that filter, plus the request's video and photo options, reads each eligible item's id, path, play count, last played, date added, modified time, and rating, and, only while Spread by tags is on, every item's tags in one read, then reads the picked item by id, and does not keep a full-catalog cache. `POST /api/random` picks with the options its request sends, each missing one at its default: Shuffle with Remember plays for 1, 7, 30 (the default), or 90 days or until everything has played, and Spread by folder, on by default, and Spread by tags (off, all tags, or by category), Favor less played, Favor newly added, Favor newly created, and Favor higher rated, off by default. Any other window reads as 30 days, and a null or unknown Spread by tags as off. Every pick goes into a memory kept per `clientId` by item id and pick time, which a change to the filter or the options keeps and a server restart clears, and each pick drops the memory of every device whose last pick is past its window. Shuffle leaves out the files picked within the window, and once every eligible file has been picked they start a new cycle whose first pick is never the last pick. Spread by folder looks back over the last 16 picks, or over half the eligible set's folder count, rounded down, when that is fewer, and leaves out the files in those picks' folders unless they hold every file left. Spread by tags makes files whose tags came up in the last 16 eligible picks beyond their share less likely, Favor less played, Favor higher rated, and the 20% share of files added or created in the last 14 days weigh the rest, and Core's engine decides the odds. The answer carries the picked item, or null when nothing is eligible, and the device's Shuffle cycle numbers, `POST /api/random/cycle` answers those numbers for a filter and options without picking, and `POST /api/random/reset` clears the device's Shuffle memory and keeps the last 16 picks Spread looks at. Each pick writes one `last.log` line with the options that are on, the window, the eligible count, and the elapsed time. Playing one item reads that item and whether its source is enabled. `POST /api/library/item` reads one item by its catalog id and does not add thumbnail fields. Library stats include the loudness baseline and the count of rated items. An empty stored source display name is omitted. Tag-editor model reads, item-tag add and remove, category and tag upsert, rename, and delete, and auto-tag apply update catalog rows. Favorite, blacklist, rating, record-playback, and clear-stats update those rows, finding items by catalog id only, matched exactly, so a full path or an id in other casing finds no item; auto-tag apply alone finds its files by full path. `POST /api/bulk/item-state` sets or clears favorite or blacklist, with the same rule, and `POST /api/bulk/rating` sets or clears one rating, on many items in one write, skipping ids no item has, and each publishes one event for the request when any named item is in the library; the single favorite, blacklist, and rating routes write through the same code. `POST /api/library/query-ids` answers the id of every item the library query with the same filter and search matches, with no paging or cap, for selecting them all, or, with `itemIds`, only those of them that match, for checking a selection. `POST /api/library/delete-files` deletes the named items' files from disk outside the operations lock, then removes the items whose files it deleted, with their tags, in one write, and keeps an item whose file isn't on disk or can't be deleted, naming it in its answer; it is an admin action, accepted by the `/control` routes' check, so from another machine only with a control session or the control token, and any other caller gets 403 with `control_token_required`. A tag-editor model read with `countsOnly` answers how many of the items hold each tag in place of each item's tags. `POST /api/rating` sets an item's rating, in stars, a multiple of 0.5 from 0.5 to 5, or clears it with null, refusing any other rating with 400, and changes neither favorite nor blacklist. A favorite clears blacklist, and a blacklist clears favorite. Clear-stats clears every played row only with `allItems`, and an id list clears only those items; a request with neither, or both, is refused and clears nothing. It answers `count`, how many of the named items are in the library, or every item with `allItems`, and publishes `resyncRequired` when it cleared any item's stats. Library stats are one SQL pass grouped by source id and media type: an item counts toward the source whose id it holds, and is a photo when its media type is photo and a video otherwise. Auto-tag scan and duplicate scan read catalog rows. A full-library auto-tag scan reads every item, and any other scan reads enabled sources. Duplicate groups include only ready fingerprints. Duplicate apply deletes the non-kept files and rows through the delete-files code, takes the same admin check, and publishes `itemsRemoved`. Source import inserts new files and updates existing paths. The disk walk does not hold the catalog lock. An existing path keeps its id, tags, favorite, blacklist, and playback stats. Files missing on disk stay until refresh. Refresh removes items whose files are gone, except from a disabled source, a source whose folder is missing, or a source whose folder exists but lists no media files while the library holds items from it, such as a mount point whose drive or share isn't mounted: those items stay, and in that last case `last.log` gets a warning naming the folder, and the refresh status lists the source by id with its kept item count in `keptSources`, which each run starts empty. Refresh writes the columns each stage owns as that work finishes. Every file one refresh adds gets the time its source stage started as its date added, and a file moved or renamed within a source, matched by its fingerprint, keeps its row and its date added. A favorite, tag, blacklist, or playback change that commits during a stage stays. Thumbnail reuse trusts the revision stored on the item, which is that item's fingerprint, size, and write time, and does not walk those source files when that revision still matches. The stage writes that item's revision, width, and height as the item finishes. Browse reads those dimensions from the item row. `hasThumbnail` is still whether that item's JPEG exists. When the thumbnail stage completes, a JPEG whose item is not in the catalog is deleted, and the finished refresh's summary reports that cleanup. Opening the catalog does not delete those files. There is no thumbnail file-count or byte cap. A catalog backup for that refresh is taken after the refresh finishes and still follows the backup gap. A shorter backup gap applies on the next catalog save. Opening the catalog does not read it whole. The source list and source enable and disable read catalog rows, so an imported source is listed and can be toggled without a restart. The tag table is the catalog's tag list. An item can still hold a tag name that is not in that table.
  - `POST /api/play/{itemId}` (persisted library **id** only): returns `PlaybackItemResponse`, the item a random pick carries, records playback server-side, and emits `playbackRecorded` on SSE, unless its body's `recordPlayback` is false, which answers the same without either; deterministic `404` / `409` / `415` errors with optional `code` on `ErrorResponse`. The play read is that item and its source. Direct play does not block blacklisted items; callers must not double-call `record-playback` for the same start.
  - `POST /api/play/{itemId}` and `GET /api/media/{token}` open the file to tell a missing file (`404`) from one that is there but can't be read (`503`, with `play_media_unreadable` on play), such as on a stalled drive or share, and log the unreadable answer to `last.log` without the path.
  - Filters can keep only files a browser can play: `onlyBrowserPlayable` keeps photos and the videos whose file name ends in `.mp4`, `.m4v`, or `.webm`, in the library query, its counts, and random selection. The scan adds `.m4v` and `.webm` files with the other supported video and photo types.
  - Filters can keep only unrated items, or items rated at or above a minimum: `onlyUnrated` keeps items with no rating, and `minRating`, in stars, keeps items rated at or above it, so it leaves unrated items out, in the library query, its counts, and random selection. The library query also sorts by `Rating`, with an unrated item as 0 stars.
  - Filters can keep items by their date added and their date created, the file's modified time: `addedRange` and `createdRange` each hold a preset, `last7Days`, `last30Days`, `last90Days`, or `thisYear`, or a custom range of days, and the server resolves them each time it filters, in its own time zone and to whole days, in the library query, its counts, and random selection. An item without that date is left out. Core's preset comparison compares them by the choice, and the WebUI's Filter tab sets them. The library query sorts by `DateAdded` and `DateCreated`, and library items carry `dateAddedUtc` and `dateCreatedUtc` when the catalog has them.
  - Presets: each has an id of its own, kept across renames, which `GET /api/presets` returns and the random request's `presetId` names. `POST /api/presets/create`, `POST /api/presets/{presetId}/update`, `POST /api/presets/{presetId}/rename`, `POST /api/presets/reorder`, and `POST /api/presets/{presetId}/delete` write one preset, or the order, and publish `presetCatalogChanged` with the preset's id, or none for a reorder, and the request's `clientId`. A preset holding the default filter, another preset's filter, or another preset's name is refused, and a write the catalog doesn't take answers 500 and gets a `last.log` warning. The WebUI's Filter tab saves each preset it changed through them, one at a time, and every open WebUI reloads its presets on the event.
  - Every event and response that names a library item carries its catalog item id: `PlaybackItemResponse.itemId` (its `id` is the full path, which the Stats tab shows), `playbackRecorded.itemId`, `itemTagsChanged.resolvedItemIds`, the record-playback response, auto-tag scan files and apply results, and duplicate-apply failures. `itemStateChanged` also carries `previousIsFavorite` and `previousIsBlacklisted`, and `clientId`, the client whose favorite or blacklist request made the change, which the WebUI sends. `itemRatingChanged`, published only when a rating changed, carries the item's id and path, its `rating` and `previousRating`, in stars or null for none, and the `clientId` of the rating request. `bulkItemStateChanged` and `bulkItemRatingChanged` carry what the bulk request set, `count`, the named items in the library, the items that changed with their values before and after, and the request's `clientId`, and `itemsRemoved` the ids of the items delete files or duplicate apply removed. Library items carry `durationSeconds` beside the `duration` string, and a rated item its `rating`, in stars from 0.5 to 5 in half-star steps. Random picks and library plays (`PlaybackItemResponse`) carry the video's `integratedLoudness` and `peakDb` too, null where the loudness scan hasn't measured them, for loudness normalization. They also carry the item's `rating`, in stars from 0.5 to 5 in half-star steps, or null for none.
  - Unified refresh pipeline: stage/status projection, a name sort key stage that fills missing keys and recomputes every key after a key version change, thumbnail generation, library **duration** / **loudness** via **ffmpeg**/**ffprobe**, and server-scheduled **auto-refresh**. The loudness scan measures integrated loudness and true peak with `ebur128`, one video at a time, stores no value where it measured none, counts a track it measures as digital silence, at the -70 LUFS floor with no peak, as no audio, the same as a file without an audio track, and records the loudness analysis version, so a video with audio scanned under an older version is scanned again. A scan that fails keeps the stored loudness and peak and records its error, and the next refresh scans that video again. Server shutdown cancels a manual or automatic refresh in progress and does not record that cancellation as a pipeline failure or a completed refresh. Catalog updates that stage has already written stay. A forced duration or loudness rescan stays pending when shutdown cancels that stage. Saving refresh settings schedules the next automatic refresh from the new interval, and clearing a forced rescan keeps the other refresh settings. Clients send refresh **settings** (for example enable/interval) and consume library state via API/SSE only (no authoritative client-side refresh stages or local ffprobe for catalog duration).
  - Replay-aware SSE envelope with reconnect recovery (`Last-Event-ID`, `resyncRequired`, authoritative requery). The WebUI resumes its event stream with the last event ID, and takes the revision of a `resyncRequired` it receives. The server also publishes `resyncRequired` to every stream after clear-stats, and in place of a `bulkItemStateChanged`, `bulkItemRatingChanged`, or `itemsRemoved` that would list more than 1,000 items, with `last.log` saying so; a published one carries the revision before it as `lastEventId` and its own as `currentRevision`. A stream opened without a last event ID starts with a `streamOpened` event carrying the server's current revision, so a client that receives no other event still resumes from it, including from 0. A last event ID ahead of the server's revision, as after a server restart, gets `resyncRequired`. Duration and loudness refresh progress is published at most every 500 ms, like fingerprint and thumbnail progress, plus each stage's completion.

- **WebUI client (`src/clients/web/ReelRoulette.WebUI`)**
  - Runtime-config bootstrap, direct API/SSE integration, and compatibility/capability checks of `/api/version` at startup, each time the event stream opens, or fails while the server doesn't ask for pairing, and every 3 seconds while the stream is open and the last check didn't reach the server, one at a time, each given up after 10 seconds. Presets, the library, and a panel remembered open load when a check first finds the server compatible with a library, and not again while later checks find it still so. A check answered with 401 counts as not ready, so once the device pairs, the presets load again, the Library tab loads when it has no page, and a Filter or Tags tab that shows loads again.
  - The page is a Preact root with `@preact/signals` shared state. The header (logo, pairing prompt, now playing), the player and its controls (with fullscreen, swipe, tap, and double-tap gestures, and the empty state), the side panel with its Library, Tags, Stats, Filter, Randomization, and Settings tabs (the library, the tag editor, the stats, the filter, the random pick options, and the settings), Auto Tag, the in-app dialogs, the popups and the list behind the player's bell, and the server connection are components and typed modules. A screen that fails to render stops showing, relays `ui-error screen=<name> error=<type>` to `last.log`, and leaves the others working. A startup error shows its message as text.
  - Session-aware identity propagation (`clientId`/`sessionId`) through API + SSE paths.
  - Core playback/control/tag workflows aligned with server-authoritative behavior. The player's favorite and blacklist take the server's answer for the item the request was for, even after another item plays, and each play answer's flags and rating for its item; on `resyncRequired` the player forgets the item states it kept and reads the playing item again (`POST /api/library/item`), taking its favorite, blacklist, and rating.
  - One random pick at a time: a press while one is waiting sends nothing, and a pick the server does not answer within 10 seconds is cancelled, shows "No response from the server. Try again." in the in-app notice, and relays a `playback=random-pick-timeout` line to `last.log`. The player's Random button (`casino`), between Next and Loop, picks from anywhere in the history, as R does, and puts the pick where the Randomization tab's Random behavior says: at the end with Jump, the default, or right after the playing item with Insert, keeping every entry either way; a file Insert put there that can't play is skipped by picking again with Insert. Every other random pick, Next and autoplay at the end of the history and Play with nothing playing, goes at the end, while a file chosen from the library drops the entries after the playing one. Each pick sends the Randomization tab's options, and its answer brings this device's Shuffle cycle numbers, which the cycle card shows.
  - Player indicator: one lasting state at a time shows at the player's top center at every width, the first active one in this precedence order, so it never alternates: Reconnecting… (`sync`, spinning) while the last version check didn't reach the server, or the event stream has failed and isn't open again, though not before the first check answers, nor while the last check found no library, nor while the server asks for pairing, since the server then refuses the stream; Server not compatible (`sync_problem`, an orange warning) while the server fails the compatibility check; Running without a library (`warning`, orange) while the last check reported a library state other than ready; Loading… (`progress_activity`, spinning) once a random pick, a library play, or a media load has waited half a second, counted once from the first wait until every wait ends, so a quick load shows nothing; and a running refresh, "Library refresh: {stage} ({percent}%)", with the stage's label ("Starting", "Refreshing sources", "Sorting names", "Fingerprinting files", "Scanning durations", "Scanning loudness", "Generating thumbnails"), shown only while the player's controls show, and cleared when a refresh status isn't running and on `resyncRequired`. Reconnecting… ends once the stream is open and a check reaches the server, and Running without a library once a check reports the library ready. Nothing shows while the server asks for pairing. A media load's wait ends on its `playing` or load, a rejected `play()`, or a pause by the user or Auto-Pause, never by a timeout, and buffering partway through a video doesn't count; after its error it lasts until the server's answer has stopped the player, skipped the file, or given it a fresh media URL, and a history step's wait for its fresh media URL lasts until the server answers, through Auto-Pause. It stays clear of the corner buttons on both sides and ends a long state in an ellipsis; on a player narrower than 600 px, which the page measures and marks with `is-narrow` on the player column, it sits below them. Each state relays its text to `last.log` once when it starts showing, and a refresh once per stage. None of these states pops up; the list behind the bell shows each active one under Now.
  - A running refresh shows on the player's indicator, and how it ended pops up: "Library refresh finished" with its consolidated summary as the second line, one segment per stage separated by " · " (including the Fingerprint segment), or "Library refresh failed" with the server's error as the second line, a warning; `last.log` gets the summary but not the error, which can name a file or folder. A run that ends without finishing or failing, such as one cancelled at shutdown, relays "Core refresh idle." and shows nothing. The theme is the Settings tab's Theme: System, the default, follows `prefers-color-scheme` as it changes, and Dark or Light holds whatever the system says, as `theme-dark` or `theme-light` on the root element, which the stylesheet reads. The `theme-color` meta and `apple-mobile-web-app-status-bar-style` follow the theme in use: `#1a1a1a` and `black-translucent` in the dark theme, `#eceff4` and `default`, for dark status bar text, in the light. An inline script in `index.html`'s head applies the theme kept on this device while the page loads, before it paints and before an installed iOS app reads its status bar style, and the build output check fails unless the built page keeps that script.
  - Notifications: a lasting state shows on the player's indicator, a one-off message pops up and the list behind the player's bell keeps it, anything to act on shows in the in-app notice and the list keeps it, a field problem shows in its field, and a message shown in place, such as the library's load failure or the preset dropdown's error, stays there and only relays; there is no status line, and no diagnostics line below the player. Every message's text is relayed to `last.log` as a `status=` line, a repeat within a second once, as are the texts that show nothing, such as "Ready (API 2)", "SSE connected", and "Playing". Popups sit beside the player at the position the popup settings say, bottom center by default, 12 px up, rising above the player's controls while those show unless the overlay panel covers the player, and on a phone on its side, outside pseudo-fullscreen, clear of the home indicator too; at a top position they start 64 px down, below the indicator on a player narrower than 600 px. Each is a card with its kind's icon, the message, an optional second line, and Dismiss. At most three show, newest nearest the edge, and a fourth closes the oldest that isn't a warning, so while three warnings show nothing new pops up; a popup with the same key, such as a second favorite change, replaces the one showing in its place and starts its time over. A popup closes after the popup time, 5 seconds by default, with a 160 ms fade, and a warning stays until it is closed.
