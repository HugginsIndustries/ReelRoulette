Commit Message:

Bugfix: Keep tag filters fast at any tag count

- The tag filter builds one set of item ids for the whole filter, each category group being the items with any or all of its tags and the groups intersected or united by the global mode, and checks each item against it once with `+items.id IN (…)`. Browse counts, pages, and random eligibility no longer run a correlated subquery per tag for every item, and excluded tags are one `NOT IN` set.
- Tags match by name fold, as the catalog identifies them, instead of an OrdinalIgnoreCase collation, for items and for the category lookup. Results change only for names where the two disagree, such as the Kelvin sign and final sigma.
- The browse count, page, and random candidates SQL come from shared builders, so tests check the query plans the server runs.
- Tests cover tricky names and edge cases, 400 seeded random filters against an in-test reference, and identical query plans with no correlated subqueries at 1 and 27 tags.
- Evidence on a scratch copy of a 49,055-item catalog: the old and new Core returned identical candidates, counts, and two pages for all 28 saved presets and 300 seeded random filters, 0 mismatches. The 27-tag preset's candidate query took 44 ms instead of 698 ms and its uncached first page 92 ms instead of 1,468 ms.
